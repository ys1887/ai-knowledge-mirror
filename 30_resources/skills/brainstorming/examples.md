# Brainstorming Skill Examples

このファイルは、`brainstorming` スキルの実運用イメージを示すサンプルです。

## Example 1: 機能要件の具体化（1問ずつ）

### User
管理画面に「一括承認」機能を追加したい。

### Assistant
最初に対象を絞ります。次のどれが主目的ですか？

1. 対応時間の短縮（運用効率）
2. 承認漏れの削減（品質）
3. 権限統制の強化（セキュリティ）

### User
1がメイン。

### Assistant
ありがとうございます。次の確認です。1回の一括承認の上限件数はどれが適切ですか？

1. 50件
2. 100件
3. 上限なし（非推奨）


## Example 2: 2-3案の比較提示

### Context
- 既存APIは単体承認のみ
- 監査ログは必須
- UIは一覧テーブル

### Assistant
推奨案から共有します。

**Option A (Recommended): バルク承認APIを新設**
- 長所: 処理効率が高く、UIとAPIの責務が明確
- 短所: API追加と権限チェック実装が必要
- 向いている条件: 今後もバッチ操作が増える

**Option B: 単体承認APIをクライアント側で並列実行**
- 長所: サーバー変更が最小
- 短所: 失敗時の整合性管理が難しい
- 向いている条件: 一時的な対応

**Option C: 非同期ジョブ化（キュー投入）**
- 長所: 大量件数でも安定
- 短所: 実装コストが高い
- 向いている条件: 大規模運用が確定している

推奨は Option A です。理由は、現状要件（効率化 + 監査ログ必須）に対して、拡張性と運用性のバランスが最も良いためです。


## Example 3: 設計を小分けで合意する

### Assistant (Section 1/3: Architecture)
- フロント: テーブル選択 + 一括承認アクション
- API: `POST /approvals/bulk`
- サービス: 入力検証 -> 権限確認 -> 承認実行 -> 監査ログ

ここまでの構成は問題ないですか？（OK / 修正あり）

### User
OK。

### Assistant (Section 2/3: Error Handling)
- 部分失敗を許容し、成功/失敗件数をレスポンスで返す
- 権限不足レコードはスキップし理由を返す
- 監査ログは成功・失敗の両方を記録

この方針で進めて問題ないですか？


## Example 4: 完了時の成果物

### Assistant
合意内容を `docs/plans/YYYY-MM-DD-bulk-approval-design.md` 形式で保存できる状態に整理します。
実装に進む場合は、次の順序でタスク化します。

1. API契約の確定
2. サービス実装（権限・監査ログ含む）
3. UI実装（一括選択 + 実行 + 結果表示）
4. テスト追加（unit/integration）
